# ACE-Step 1.5 性能优化日志

- 分支：子仓库 `qnn-perf`（基于 `qnn-analysis`）
- 环境：qiao-ubuntu，RTX 4060 8 GB（实测 bf16 GEMM 约 29 TFLOPS、显存带宽 251 GB/s），PCIe 实测约 10 GB/s，torch 2.10.0+cu128，flash-attn 2.8.3，triton 3.6.0，12 核 CPU / 15 GB 内存
- 场景：text2music，30 s 歌曲，batch 1，0.6B 5Hz LM（CoT + 语义码）+ turbo DiT 8 步（shift 3）+ Oobleck VAE；固定全局种子，输出可复现
- 指标：端到端墙钟（`qnn/perf/bench_e2e.py`，1 次预热后测 N 次）。下表“稳态”取第 3 次及以后测量的中位数，以排除 LM 头两次生成偏慢（见候选 #5）
- 正确性：
  - 不改数值的改动要求输出 md5 不变；
  - 改数值的改动与参照比较 SNR，或用仓库自带的 PMI 奖励做质量比较
- 环境说明：`pytorch_wavelets` 未安装，DCW 在所有配置下都静默退化为 no-op，对比公平

## 本轮发现的问题

- **主机内存是 8 GB 档卸载方案的真正约束**。15.8 GB 的主机上，pinned 主副本 5.9 GB 加上进程本身约 2.5 GB，峰值约 8.5～9 GB。加载 11 GB 权重时，页缓存会把匿名页挤到 swap，只影响冷启动；系统的 swappiness 设置没有改。
- **8 GB 档声明的 480 s 上限做不到**：vllm 后端在低显存模式下只能生成约 397 s（见上）。按 KV 容量（30 块共 7680 token）估算，改成 4096 应该放得下，但会改变默认行为，交给用户决定。
- 上一版文档说“nano-vllm 的 ACE fork 去掉了 torch.compile”是错的：RMSNorm、SiLU、RoPE、Sampler 都用 `maybe_compile` 编译融合了，已更正。

# 第三轮（分析）：batch 与 continuous batching

- 日期：2026-11-21；起点：qnn-perf `560c9bd`（第二轮最终配置 F：vllm + offload + offload-dit + flash）。
- 口径：`bench_e2e.py --phases --runs 2`（各阶段同步计时，比 F 的墙钟多约 0.3 s，所以 b1 重测作为同口径对照）。
- 新增：`bench_e2e.py --batch N --no-batch-guard`、`batch_table.py`（汇总表）、`overlap_bench.py`（跨请求流水上限）。
- 结果：`BAT_<长度>s_b<N>/`、`BATNG_*`（绕过 VRAM guard）、`overlap_bench/`。

## 现有 batch 机制

- `GenerationConfig.batch_size`（默认 2）：同一个 prompt 生成 N 个候选。
  - LM Phase 1（CoT）只跑一次，元数据复制给 N 条；
  - Phase 2 一次 `generate` 提交 N 条（CFG 成对，共 2N 条序列），nano-vllm 调度器做连续批处理；
  - DiT 按 batch 维一起扩散；VAE **逐条顺序解码**（`vae_decode_chunks.py:37`）。
- 外部接口只接受一个 caption / 歌词 / 时长，不能把不同请求合成一批；API 只有 1 个队列 worker，请求串行执行。
- VRAM guard（`memory_utils._vram_guard_reduce_batch`）：offload 模式下 batch ≤ 档位上限（8 GB 档为 2）时直接放行；超过上限才测空闲显存。它测量时 DiT 已经预取进显存，只看到 1.6 GB 空闲，于是把 batch 降为 1。**此时 LM 已经生成了 N 条码，多出的码直接丢弃，调用方也只拿到 1 首**。

LM 在默认 stream 上跑（主线程），另一个请求的 8 步 DiT 在非阻塞副 stream 上跑（另一线程），两者模型都常驻显存：

| - | - | - | - | - | - | - | - |

| 120 s | 4.29 | 1.61 | 5.90 | 5.80 | 0.10 | 1.61 | 5.12 GB |
| 240 s | 8.32 | 3.71 | 12.03 | 11.93 | 0.10 | 3.71 | 5.20 GB |

## 结论

1. **LM：合批几乎免费，收益真实**。Phase 2 从 1 条到 4 条（2→8 条序列），每步耗时只增加 7～28%（30 s：0.88→1.04 s；120 s：3.56→4.56 s）。原因是 decode 受带宽限制，每步都要读一遍 1.2 GB 权重，与序列条数无关。Phase 1 在同 prompt 合批中只跑一次，均摊后完全免费。
2. **DiT：只有短歌能从合批获益**。10 s 时 b4 的每首耗时降到 0.57×，30 s 时降到 0.77×。≥60 s 时每首反而变慢 1.1～1.2 倍（60 s b4：3.58 s，单条 4×0.81=3.24 s；120 s b2：3.64 s，单条 2×1.61=3.22 s）。750 帧以上已经算力饱和，合批只会增加中间张量。
3. **VAE：没有收益**。它本来就逐条顺序解码，每帧耗时从 256 帧窗口起已经持平（第二轮 `vae_mem_curve`），把多条拼进同一窗口也不会更快。
4. **端到端吞吐**：短歌明显受益，10 s b4 为 2.95×，30 s b4 为 2.32×；120 s b4 只有 1.63×，基本全部来自 LM；240 s b2 反而更慢（0.88×），而且主机开始用 swap（1.1 GB，墙钟在 26～45 s 之间波动，原因未查明）。
5. **显存上限**：b4（≤120 s）峰值为 6.91～6.99 GB 已分配、7.05～7.13 GB reserved，离 7.6 GiB 只剩约 0.5 GB；b8 在 10 s 和 30 s 都 OOM。8 GB 档把上限定为 2 是合理的，放到 4 风险偏高。
6. **跨请求流水（stage 级 continuous batching）不可行**：LM 和 DiT 并发只省 0.1 s（理想值是 0.5～3.7 s）。DiT 的 GEMM/attention kernel 占满所有 SM，LM 的小 kernel 只能排在后面。GPU 是真正的共享瓶颈，两个阶段之间没有可以填的空隙。
7. **跨请求 LM continuous batching（不同 prompt 合进同一次 decode）**：理论收益与第 1 条相同，但受 KV 容量限制。低显存模式下 KV 共 30 块 × 256 = 7680 token，每个请求（CFG 成对）约占 2×⌈(P+5L)/256⌉ 块（P 为提示长度，约 400）。估算 30 s 最多约 5 个请求、120 s 约 3 个、240 s 约 2 个同时在跑（估算，待验证）。端到端收益还要扣掉 DiT/VAE 部分：
   - 30 s：LM 占 1.7/3.45 = 49%，LM 部分做到 3× 时端到端约 1.5×；
   - 240 s：LM 占 53%，KV 只容得下 2 个请求，端到端约 1.3×。
   而且还要实现跨请求聚合（新接口、按时长分桶、首请求等待窗口），会增加单个请求的延迟。

## 建议

- **不改代码路径**：对单用户、单请求，batch 不降低延迟（b2 的墙钟总是比 b1 长）。最优仍是 batch 1。
- **同一 prompt 要多个候选时**（UI 默认 batch 2），现有 batch 已经是正确做法：10～60 s 吞吐提升 1.44～1.79×。
- **长歌（≥240 s）不要用 batch 2**：每首更慢，而且触发 swap。可以考虑让 8 GB 档按时长收紧上限（例如 >120 s 时上限为 1）。这会改变默认行为，交由用户决定。
- **修 guard 的静默降级（候选）**：在 LM 之前就按档位裁剪 batch（或者把它挪到 LM 前面），避免白生成码、返回数量与请求不一致。当前只有绕过档位上限（batch > 2）时才会触发。
- 不建议实现跨请求流水或跨请求 continuous batching：在 8 GB 单卡上，前者实测无收益，后者被 KV 容量和 DiT 算力饱和限制在约 1.3～1.5×，而且以增加延迟为代价。服务多用户、追求吞吐的场景应在更大显存的卡上做（KV 和 DiT 激活都有余量）。

## 第三轮落地（O14）：按显存规划 batch

用户要求按上面的建议实施；长歌的 batch 上限不写死时长，而是按显存估算。项目策略（档位）可以按这张卡的实测直接修改。

### 先纠正上面的两个结论

- **240 s b2 的 swap 与 batch 无关**。重测 240 s b2（`PK_240s_b2`）：24.78 s，每首 12.39 s，比 b1 快 1.28×，没有 swap。同一轮里 120 s 的 **b1** 反而出现了 1.6 GB swap、27.8 s。swap 来自系统残留状态（启动时系统 swap 已有约 1 GB），不是 batch 造成的。因此长歌也不需要禁用 batch，只需要显存够用。
- **guard 的“空闲 1.6 GB”是在 DiT 预取之后测的**，这一点不变。

### 分阶段显存峰值（`bench_e2e --phases` 新增 `phase_peak_gb`，嵌套安全）

峰值始终出现在 `M.prepare_condition`（整个 DiT 在 GPU 上）。各长度 × batch（`PK_*`，绕过 guard）：

| 长度 | b1 | b2 | b4 | b6 | 每首增量 GB |
| - | - | - | - | - | - |
| 10 s | | | 6.908 | 6.997 | 0.045 |
| 30 s | 6.773 | 6.822 | 6.923 | | 0.050 |
| 120 s | 6.793 | 6.858 | 6.993 | | 0.066 |
| 240 s | 6.815 | 6.904 | | | 0.089 |

拟合：每首增量 = 0.041 + 8e-6 × 帧数（GB），残差 ≤ 0.01 GB；固定部分 = 规划时已分配的显存 + DiT 权重（4.46 GB），几乎没有额外常数。

### 新发现：VAE 的 weight_norm 权重在卸载后仍留在 GPU 上（0.17 GiB）

- 现象：第一次生成之后，规划时测到的空闲显存从 5.12 GB 降到 4.93 GB，`memory_allocated` 从 2.09 GB 变为 2.26 GB，而且每次生成后都保持这个值。
- 定位（`vram_leak_probe.py`）：gc 里找不到新增的 CUDA 张量；按分配调用栈统计，全部来自 `autoencoder_oobleck.py` 的前向（conv_t1 94.6 MiB，各残差单元 conv 18.8 MiB×3……）。
- 原因：Oobleck 使用旧式 `torch.nn.utils.weight_norm`，它的前向 pre-hook 每次计算 `weight = g·v/‖v‖` 后用 `setattr` 挂到模块上。这个张量既不是参数也不是 buffer，卸载时只搬走了 g 和 v，算出来的 weight 一直留在 GPU 上。原始的 legacy 卸载路径同样有这个问题。
- 修复：`pinned_offload.release_derived_weights()` 在卸载时把它置为 None（下次前向由 hook 重新计算，数值不变），pinned 和 legacy 两条卸载路径都会调用。
- 效果：残留 0.17 → 0.012 GB；30 s b1 峰值 6.773 → **6.615 GB**；码和波形 md5 不变（8669ef94f6 / 3a042dbc3a）。

### 新发现：nano-vllm 在 KV 不足时，batch 码生成会崩溃

- 240 s b3（`PK_240s_b3`）：`The size of tensor a (2) must match the size of tensor b (3)`。
- 原因：3 首 × CFG 成对 × 每条约 7 块，共需 42 块，而 8 GB 卡只有 30 块 KV。调度器抢占时只抢占单条序列，把 CFG 对拆开了，落单的 uncond 被单独调度。即使不崩，抢占也会让共享的约束解码状态（只按第一条序列更新）不同步。
- 修复：`_run_vllm` 用 `_vllm_items_per_call` 计算一次能放下几首（每条序列按 提示长度 + max_tokens 向上取整到块，CFG 计两条，不计前缀共享），超出时分组顺序生成，从而避免抢占。单首或放得下时仍是一次调用。

### 规划器（`batch_plan.py`，`MemoryUtilsMixin.plan_batch_size`）

```
budget = 有效空闲显存(设备空闲 + 分配器缓存) − 仍在 CPU 上的 DiT 权重 − 0.3 GB 余量
batch  = min(请求, ⌊budget / (0.041 + 8e-6·帧数)⌋, ⌊(主机 MemAvailable − 1 GB) / (1.5 MB·秒数)⌋)
```

- **不受当前状态影响**：已经预取到 GPU 的权重算在已分配里，还在 CPU 上的单独加上，所以在 LM 之前和之后算出的结果一致。实测 LM 前空闲 5.12 GB、LM 后（DiT 已预取，allocated 5.43 GB）空闲 1.76 GB，两次都给出相同的 batch。
- 余量 0.3 GB 的依据：10 s b8 在预测余量 0.12 GB 时 OOM，余量 0.20 GB 时正常（均为修复残留之前的测量）。
- 时长未知（由 LM 决定）时按档位的最大时长估计，保证 LM 之后不需要再缩小 batch。XL 模型每首 ×1.7，base（CFG）每首 ×2。
- `inference.generate_music` 在 LM 之前调用规划器，LM 和 DiT 都使用规划后的 batch（DiT 原来收到的是 `config.batch_size`，现在改为实际 batch）。DiT 侧的 guard 也改用规划器，去掉了“offload 且 ≤ 档位上限就跳过检查”的分支。
- tier3（6–8 GB）的 UI 上限 2 → 4（含 LM 与不含 LM），每次请求再由规划器裁剪。
